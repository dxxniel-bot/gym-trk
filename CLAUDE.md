## Architecture
- **`index.html`** — the ENTIRE app (HTML + CSS + JS inline). Single-page, JS-rendered screens via a `render()` router on `state.screen`. ~all logic here.
- **`manifest.json` + `sw.js`** — PWA (installable + offline). `sw.js` is **network-first** for same-origin (online = latest deploy, offline = cache) — cache name bump (`gymtrk-vN`) forces refresh.
- **`*-prototype.html`** — static design references (superseded by `index.html`; keep for design history).

- **No-data-loss rule:** keep the LS key stable, never clear it, migrate additively in `migrate()`. Editing code never touches LS. `[settings]` has export/import JSON (backup) + "log in" restores from a pasted backup.
- **Identity/variant engine (v206–v210, 2026-07-25; ladder extended v215):** exercise edits are per split-DAY instance, never global by name — `saveExEdit` merges into (never replaces) the exercise at `db.split.days[di].exercises[ei]`; editing "chest press" on day A never touches a same-named exercise on day B, and the mid-session editor no longer mirrors into the split at all (opt-in `ee_tosplit` checkbox, off by default). `variantKey(e)` = `canonType(type)+uni+assisted+weighted[+cardioSub]` — same name, different variant (machine vs. free, bilateral vs. unilateral / **UNI≠BI always chipped**, assisted vs. weighted, cardio subtype) is a fully independent history/prefill/%. Prefill (formerly "v68", now baseline-driven) and progress % both resolve against the **equivalent antecedent** via `baselineSetsFor()` — ladder (exact `exId` → same day+name+variant+occ → unique day+name+variant → same day+name+variant any occ → unique name+variant nearby → unique name+variant any position → name+variant most recent) — NEVER bare name alone (UNI/BI and free/machine stay isolated). `alignSetIdx()` then pairs today's sets to the baseline's like-for-like (drop/non-drop, side, ordinal) instead of a positional clamp, so an unmatched extra set shows no badge instead of a false one. `%`/progress badges use `sessionFatigueContext()`+`correctedE1RM()` (fresh-equivalent, discounting intra-session fatigue from primary AND weighted secondary muscles) with confidence tiers (`progConfidence`) so a weak match shows `~` and a wide mismatch shows direction only, never a fabricated number. Muscle-volume attribution (`musclesOf()`) resolves **at read time** from the split via `exId`, never mutating saved sessions — "lo que hiciste es inmutable; cómo se clasifica se resuelve en vivo": add triceps as a secondary to an existing exercise and every past session under that `exId` counts toward triceps in //VOLUME retroactively, with zero rewritten data. Drop sets are subseries of their parent working set (array stays flat, `isDrop` flag as before — the 4 existing 0.5-weightings are untouched), inserted via `dropInsertIdx()` immediately after their parent + any drops it already has (never appended to the end), numbered `1, 1.5, 2, 3` via `setLabels()` (chains to `.6`/`.7`); `emptySet()`'s clone-template no longer leaks `isDrop` onto a plain `[+ set]` add. Bodyweight exercises show `[BW <live kg>] [+lastre]`: `latestBodyweight()`/`effW()` always recompute from the most recent `db.bodyweight` entry (never a frozen per-set snapshot, including for past sessions), `bwMissing()` surfaces "BW sin peso" instead of silently scoring against 0. History editing (`state.screen='histedit'`, `state._histSessId`) reuses the exact live-session row components (`renderSetRow`'s new `actPrefix` param dispatches to isolated `h_*` handlers — `h_setf`/`h_done`/`h_fs`/`h_addset`/`h_dropset`/`h_delset` — that only ever touch the targeted past `db.sessions[]` entry, never `db.activeWork`) in a denser `.hist-compact` layout; it exposes full per-set correction but deliberately NOT structural edits (rename/machine-change/add-remove-exercise — those stay split/live-session decisions) and shows only an exercise-level badge, not per-set ▲▼. Permanent self-checks (`_identitySelfCheck`/`_dropsetSelfCheck`/`_baselineSelfCheck`/`_variantSelfCheck`/`_historyEditSelfCheck`) run on `?selftest=1`.

### Built-in base foods (`BASE_FOODS`)
A curated, code-embedded table (~259 entries) of generic **whole/basic foods** OpenFoodFacts lacks (huevo, res, cebolla, tortilla, frijol, aguacate, pechuga, arroz, café…). Mexican-staple + protein-leaning, broad coverage (dairy, poultry, beef/pork, fish/seafood, legumes, grains, veg, fruit, nuts/seeds, fats, sugars/condiments, snacks, supplements, beverages, prepared dishes). Each is already in canonical shape (`per100` for all MACROKEYS, `base:'g'|'ml'`, `sizes` with natural piece/serving). Built via a terse `add(name,kcal,p,c,f,opt)` helper (`opt`: `s`ugar `fi`ber `na`+`k` mg `caf` `sv`/`pc`/`ct` grams `sl` label `base` `en`=English alias). Values are ~per-100 g edible-portion USDA approximations (composite dishes are rougher). **Bilingual search** (user reported better MFP hits in English): every entry has an `en` alias and `bfNorm()` (accent-insensitive, lowercased) matches **name OR alt** — so "chicken"→Pechuga de pollo, "onion"→Cebolla. **Surfaced in search, not copied to LS:** matched in `openFoodAdd`'s inline `#fa_q` list (under a BÁSICOS group) and in `openNameSearch` (BÁSICOS above OFF PRODUCTOS). Pick → `data-act="pickbase"` → `openLog(food,{isNew:true})`; "guardar + loguear" copies it into `db.foods` (keeps its `bf_*` id, then shows under RECIENTES and is filtered out of BÁSICOS to avoid dupes). To extend: add more `add(...)` rows with an `en:` alias.

The big `BASE_FOODS` IIFE is hard to edit by exact-match; to regenerate it, write the new block to a temp file and splice with Node: `h.replace(/const BASE_FOODS=\(function\(\)\{[\s\S]*?\n\}\)\(\);/, newBlock)` (verify exactly one match first).

**`openFoodAdd(preset, lockTag)`** — the food-add sheet. Layout (top→bottom): optional COMIDA tag field + chips (a `#fa_tagtxt` input; **hidden** when `lockTag`) → `.fa-top` (search `#fa_q` + scan/search/register buttons, icon-over-label cards, equal width) → `.fa-listwrap` (RECIENTES/RESULTADOS list, fills + scrolls). `curTag()` reads `#fa_tagtxt` (works hidden). Opened from the **+ menu** (`addmeal`, editable tag) or from a **meal summary** (`addtomeal` → `openFoodAdd(tag, true)` → titled `add food · <tag>`, no tag editor, straight to the list).

## Design language
**Tres documentos, en este orden (desde 2026-09-21):** [`BRAND.md`](BRAND.md) = la identidad y lo que manda (léelo primero) · [`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md) = la referencia del estado actual (tokens, roles, fichas de componente, protocolo, auditoría) · [`DESIGN_CHANGELOG.md`](DESIGN_CHANGELOG.md) = historia (nunca implementar desde ahí). `STYLEMAP.md`, `*-prototype.html` y `mock-*.html` son históricos. Identidad: **"CMD hacker × glass moderno"** — el contenido es terminal (texto mono sobre `#000`, líneas y columnas, jerarquía por opacidad, `[verbo]` para lo puntual y un solo primario por vista, color reduccionista en el glifo o el número) y el chrome que flota es vidrio (nav, sheets, toasts, popovers). JetBrains Mono única (**600 no está cargado**), escala 10·12·16·22·34, `//` = sistema, `#` = etiqueta del dueño, `[uni]/[bi]` al frente = solo lateralidad, sus etiquetas nunca se renombran ni se ponen en mayúsculas, etiquetas de sistema en inglés y prosa en español, anillo solo en macros, lenguaje de honestidad (`~`, punteado = sugerido, gris = prefill, `—` = sin dato). Marco 393×852, gutter 18 px. Auditoría completa de diseño (2026-09-21): `../contexto/auditoria-diseno-2026-09-21.md`.
